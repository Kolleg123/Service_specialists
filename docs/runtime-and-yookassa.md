# Режимы, обновление и тестовая оплата

## Переход существующей установки

1. Уточните абсолютный путь к действующей базе. Остановите веб-процессы и фоновые задания. Сделайте резервную копию SQLite через `.backup`, например `sqlite3 /path/to/svobodno.sqlite ".backup '/path/to/svobodno-pre-upgrade.sqlite'"`. Сохраните также папку загрузок и серверное окружение. Если используете файловую копию, сначала полностью остановите все процессы, использующие SQLite, и учитывайте соседние файлы `-wal` и `-shm`.
2. Выполните первый запуск новой версии на копии с `DEMO_MODE=false` и `DATABASE_PATH`, указывающим на копию. Проверьте вход реального пользователя, историю записей и наличие назначенного администратора. Если нужен новый администратор, запустите `python -m flask --app app:create_app create-admin`.
3. Для смешанной базы проверьте список объектов, учтённых старым заполнением. Таблица `seed_entities` хранит тип и идентификатор. Принимайте решения по объектам с учётом их истории и связей с пользователями.

   ```sql
   SELECT seed_key, table_name, entity_id
   FROM seed_entities
   ORDER BY table_name, seed_key;
   ```

   В обычном режиме вход и восстановление для адресов `@svobodno.demo` и учёток из манифеста заполнения отключены. Записи, услуги, отзывы и профили из старой базы сохраняются. Подтверждённые демонстрационные профили можно скрыть в панели «Специалисты и услуги» после проверки связанных записей. Если манифест от старой версии отсутствует или учётка имела реального владельца, проверьте её происхождение по резервным копиям и истории перед выдачей нового доступа. Название профиля само по себе этого не устанавливает.
4. После проверки примените настройки к оригинальному файлу в обычном режиме. Для демо укажите отдельный новый файл `DEMO_DATABASE_PATH` и запустите отдельный экземпляр с `DEMO_MODE=true`. Для одновременного размещения используйте отдельное имя хоста. Если понадобится откат, остановите процессы и восстановите согласованный снимок базы и загрузок.

## Nginx и HTTPS

Укажите публичный HTTPS-адрес в `APP_BASE_URL` и `COOKIE_SECURE=true`. Приложение принимает переопределение IP и схемы от одного доверенного прокси. Укажите его **фактический** IP в `TRUSTED_PROXY_IPS` (например, `127.0.0.1`, если Nginx подключается по loopback TCP). Для нескольких доверенных адресов используйте список через запятую. В HTTPS-блоке Nginx задайте для Flask upstream:

```nginx
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

Оставьте upstream доступным только Nginx. Перед применением конфигурации администратор сервера проверяет её командой `nginx -t`. Для восстановления по почте серверу нужен исходящий доступ к SMTP-порту из `SMTP_PORT`.

## Тестовая оплата через ЮKassa

1. Откройте [инструкцию ЮKassa по тестовому магазину](https://yookassa.ru/docs/support/merchant/payments/implement/test-store). Войдите в личный кабинет. Выберите «Добавить магазин» → «Тестовый магазин» → онлайн-оплата. При первом входе по ссылке регистрации выберите тестирование.
2. Запишите идентификатор тестового магазина и выпустите секретный ключ в «Интеграция → Ключи API». Заполните в локальной `.env` либо в защищённом окружении веб-процесса:

   ```dotenv
   PAYMENTS_ENABLED=true
   YOOKASSA_SHOP_ID=
   YOOKASSA_SECRET_KEY=
   YOOKASSA_RETURN_URL=http://127.0.0.1:5000/?payment_return=1#dashboard
   YOOKASSA_WEBHOOK_TOKEN=
   ```

   Для сервера замените адрес возврата на HTTPS-адрес того же экземпляра. Код принимает ключ с префиксом `test_` и проверяет признак `test` у платёжного объекта. Для Windows можно выполнить оплату с локальным адресом возврата, если браузер и приложение работают на одном компьютере. Кабинет сам запрашивает статусы через сервер.

3. На отдельном публичном HTTPS-экземпляре задайте случайный токен URL командой `python -c "import secrets; print(secrets.token_urlsafe(32))"` и сохраните его в `YOOKASSA_WEBHOOK_TOKEN`. В «Интеграция → HTTP-уведомления» укажите `https://<ваш-домен>/api/payments/yookassa/<токен>` и события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Ограничьте доступ к журналам и исключите полный путь webhook из журналирования веб-сервера. Для входящих уведомлений нужен публичный HTTPS на порту 443 или 8443, TLS 1.2 или выше. Изменения Nginx и серверного окружения согласуйте с администратором сервера. [Требования ЮKassa к webhook](https://yookassa.ru/developers/using-api/webhooks).
4. Перезапустите приложение. Локально используйте `python app.py`. Для серверного экземпляра настройте запуск `python -m flask --app app:create_app sync-payments` по расписанию примерно раз в минуту с тем же окружением и файлом SQLite. Это сверяет платежи и возвраты даже при закрытых кабинетах и недоставленных webhook. На Windows для разовой сверки можно выполнить ту же команду вручную.
5. Создайте предстоящую запись с ненулевой ценой. В «Моих записях» нажмите «Оплатить» и на странице ЮKassa используйте тестовую карту `5555 5555 5555 4444`, срок из будущего и любой CVC. После возврата дождитесь «Оплачено». Для отменённого платежа создайте другую запись и используйте тестовую карту `5555 5555 5555 4600`. После отмены должна появиться возможность повторить оплату. Для проверки возврата отмените оплаченную предстоящую встречу в кабинете. [Сценарии и карты ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).

### Правила оплаты

- Запись подтверждается по действующим правилам. Оплата добровольная и доступна владельцу предстоящей записи с ненулевой ценой. Сумма берётся из сохранённого итога, включая количество участников группы.
- При закрытии страницы ЮKassa запись сохраняется. Пока платёж ожидает подтверждения, можно продолжить ту же попытку. Новая попытка доступна после подтверждённой отмены предыдущей или отклонения запроса создания. Статус подтверждает API ЮKassa при сверке, независимо от перехода по ссылке возврата.
- Одиночная и массовая отмена освобождают место по прежним правилам. Для каждого успешного платежа по отменённой записи оформляется полный тестовый возврат, в том числе если подтверждение оплаты пришло позже отмены. Если ЮKassa ещё ожидает оплату, продолжать её из кабинета отменённой записи нельзя. При позднем успехе открытой платёжной страницы применяется тот же возврат.
- Попытка создания платежа или возврата с неизвестным результатом повторяется только в пределах 23 часов. Затем статус требует сверки в личном кабинете ЮKassa. Webhook с подтверждением статуса по API и запросы по уже сохранённому ID остаются доступны. При замене магазина держите старые реквизиты до завершения незакрытых операций. [Окно идемпотентности ЮKassa](https://yookassa.ru/developers/using-api/interaction-format#idempotence).

### Повтор запросов приложения

Для POST создания услуги, ручного слота и записи браузер отправляет `Idempotency-Key`. Для повторной отправки используйте тот же ключ и тело. Сервер вернёт исходный ID. Тот же ключ с изменённым телом после принятой операции возвращает 409. Для новой операции используйте новый ключ. Старые API-клиенты могут обращаться без заголовка с прежними правилами. Состояние отправки браузер хранит в открытой вкладке. Для сверки после закрытия вкладки откройте список созданных объектов в кабинете.
