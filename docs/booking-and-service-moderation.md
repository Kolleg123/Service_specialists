# Расписание и модерация услуг

Время в API — местное время Кирова (`Europe/Kirov`, UTC+3). Даты передаются как `YYYY-MM-DD`, время как `HH:MM`, дата и время как `YYYY-MM-DDTHH:MM` без смещения. Для запросов POST остаются обязательными сессия соответствующей роли, JSON и `X-CSRF-Token`.

## T-049–T-050. Расписание и запись

| Запрос | Данные |
|---|---|
| `GET /api/master` | Кабинет мастера. Поле `schedule` появляется, когда настроено недельное расписание. `services` содержат длительность каждой услуги, `slots` — старые ручные слоты. |
| `POST /api/master/schedule` | `mode`: `time`, `day` или `manual`. Для недельного режима нужны `weekdays` (1 — понедельник, 7 — воскресенье), `opens_at`, `closes_at`. Для `time` можно задать пару `lunch_start`, `lunch_end`. Для `day` обязателен `daily_limit` (1–50). Ответ `{schedule: {...}}` или `{schedule: null}` для ручного режима. |
| `GET /api/slots/{specialist_id}?service_id={id}` | Публичный список `{slots: [...]}`. Недельное расписание возвращает `booking_mode`, `date`, `starts_at`, `ends_at`, `duration`, `price`, `remaining`, `service_id` и `id: null`. У ручного слота есть числовой `id`. |
| `POST /api/bookings` | Для `time`: `booking_mode`, `service_id`, `date`, `starts_at`. Для `day`: `booking_mode`, `service_id`, `date`. Для ручного слота достаточно прежнего `slot_id`. Выезд требует `address`. Можно передать `note` и значения `price`, `duration`, `starts_at`, `ends_at` для сверки с показанными условиями. Ответ `201 {id}`. |
| `GET /api/dashboard` | В записях есть `booking_mode`. Для `day` в интерфейсе показывается только дата. Время открытия и окончания дня используется для доступности действий. |

- Горизонт недельного расписания — 30 календарных дат, включая сегодня. Начала интервалов в режиме `time` идут с шагом в длительность услуги от открытия и отдельно от окончания обеда. Последний интервал должен полностью поместиться в рабочий блок. Активная запись на любую услугу специалиста перекрывает её интервал. Режимы недельного расписания создают записи на одного клиента. Групповая вместимость сохраняется у ручных слотов.
- Дневной лимит общий для всех услуг специалиста в выбранную дату. Каждая запись в статусе `confirmed` или `completed` считается за одну, включая старые записи и группы. Отмена освобождает место. Клиент может записаться на одну и ту же услугу один раз на дату, пока запись активна. Дата доступна до открытия, а завершение — с конца рабочего дня.
- При изменении расписания старые записи сохраняют свои начало и окончание. Активная запись на день при переключении в режим времени блокирует эту дату. Ручные слоты можно снова публиковать, выбрав `manual`. Новые интервалы записываются в существующую таблицу `slots` при бронировании, поэтому отмена, завершение и отзывы используют существующую связь `bookings.slot_id`.
- Ошибки API возвращаются как `{error: "..."}`. Типовые ответы — `400` при неверных настройках или данных, `401/403` при отсутствии сессии, прав или CSRF, `409` при занятом времени, исчерпанном лимите или изменившихся условиях. Для скрытой услуги список слотов пуст.

## T-051–T-053. Услуги

| Запрос | Данные |
|---|---|
| `POST /api/master/services` | Действующие поля `title`, `price`, `duration`, `mode`. Сервер назначает `pending`. Ответ `201 {ok, id, moderation_status}`. |
| `GET /api/master` | В `services` собственные услуги с `moderation_status` и `moderation_reason`. |
| `GET /api/admin/service-applications` | Только администратор. `{applications: [...]}` со всеми ожидающими решения услугами. Поля включают `id`, `specialist_id`, `specialist`, `title`, `price`, `duration`, `mode`. |
| `POST /api/admin/service-applications/{id}/decision` | Только администратор. `{status: "approved"}` или `{status: "rejected", reason: "..."}`. После удаления крайних пробелов причина должна содержать 1–500 символов. Ответ `200 {service}`. |
| `GET /api/services/{id}` | Публичные данные опубликованной услуги. Скрытая или неизвестная услуга возвращает `404`. |
| `GET /api/notifications` | В существующем списке есть события `service_approved` и `service_rejected` с `service_id` и `booking_id: null`. Прочтение работает через прежний маршрут. |

Статусы услуги — `pending`, `approved`, `rejected`. Публикация требует одобрения и активности услуги и специалиста. Каталог, прямое открытие, выдача слотов и создание записи используют `PUBLIC_SERVICE` из `service_moderation.py`. В поиске по названию frontend использует услуги из каталога. Повтор того же решения с той же причиной возвращает `200` без нового уведомления. Другое решение по уже проверенной услуге возвращает `409`. Неизвестная услуга даёт `404`, пустая причина — `400`.
